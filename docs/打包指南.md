# 打包指南（三端构建 / 脚本化迭代发布）

> 适用项目：Sticky Kee / 糯米（`cn.stickykee.app`）
> 三端构成：**前端** `app/`（Vue3 + Vite）→ **后端** `server/`（Go，托管前端 dist）→ **APK** `apk/`（Capacitor 壳）
> 当前版本：**v1.6.12**（versionCode 41）
> 构建方式：全部在 **Docker 容器**里完成，部署机只装 Docker + 一个 git 仓库即可，无需本机 JDK / Go / Node。

## 总览：两条脚本链路

| 角色 | 在哪台机器 | 干什么 |
|---|---|---|
| **发版机**（Windows，任意） | 有代码的机器 | `bump-version.ps1` 迭代版本号 → `git push` |
| **部署机**（Linux，装 Docker） | 服务器 | `git pull` 已由 `deploy.sh` 自动做 → `bash scripts/deploy.sh update` |

日常发版就三步：**迭代版本号 → 推代码 → 部署机一条命令**。容器负责把前端、后端、APK 全部现编现打包进同一个镜像。

```
发版机                                  部署机（Docker）
bump-version.ps1 +0.0.1                ┌───────────────────────────────────────────┐
  → 4 处版本号 + versionCode +1        │ git pull（deploy.sh 自动）               │
git push                               │ 容器① APK 编译（Dockerfile.apk-builder）    │
                                       │   版本校验→vite→cap sync→gradlew→release/ │
                                       │ 容器② 主镜像（根 Dockerfile）               │
                                       │   node 编前端 + go 编后端 + 烘焙 APK        │
                                       │ docker run 重启 + 健康检查 + 清悬挂镜像       │
                                       └───────────────────────────────────────────┘
```

## 一、版本号迭代（每次发版第一步，必做）

版本号分散在 4 处 + 1 个 `versionCode`，**必须用脚本改**，手工改极易漏（漏改 sidecar 会导致客户端收不到更新提示）。

| 位置 | 字段 |
|---|---|
| `app/package.json` | `version` |
| `apk/android/app/build.gradle` | `versionName` + `versionCode`（自动 +1） |
| `server/internal/api/handler/health_prefs.go` | `const Version` |
| `release/app_version.txt` | 版本 sidecar |

### 用法

```powershell
# 绝对版本：显式跳到 1.6.20
powershell -ExecutionPolicy Bypass -File scripts\bump-version.ps1 1.6.20

# 迭代（增量）：当前版本逐段相加，+0.0.1 = patch 自增一次
powershell -ExecutionPolicy Bypass -File scripts\bump-version.ps1 +0.0.1   # 1.6.11 → 1.6.12
powershell -ExecutionPolicy Bypass -File scripts\bump-version.ps1 +0.1.0   # minor 自增
powershell -ExecutionPolicy Bypass -File scripts\bump-version.ps1 +1.0.0   # major 自增

# 只读校验（不改动）：打印四处，不一致则退出码 1
powershell -ExecutionPolicy Bypass -File scripts\bump-version.ps1
```

脚本保证四处原子一致 + `versionCode` 单调 +1，并回读交叉校验。改完**不要**在此构建——构建交给部署机容器。

## 二、日常发版（部署机一条命令）

```bash
# 部署机 = 已 git clone 的仓库根目录，且装了 Docker
bash scripts/deploy.sh
# 等价于 bash scripts/deploy.sh update：
#   git pull → 容器编译 APK → 构建主镜像 → 重启容器 → 健康检查 → 清悬挂镜像/构建缓存
```

完成后访问 `http://<主机IP>:18480`；`/healthz` 返回 `{"status":"ok","version":"1.6.12"}` 即成功。

## 三、deploy.sh 子命令与参数速查

| 子命令 | 作用 | 典型场景 |
|---|---|---|
| `update`（默认） | git pull + 容器编 APK + 主镜像 + 重启 + 清理 | **日常发版** |
| `apk` | 只容器编译 APK（git pull + 编译），不动主容器 | 先出包验证，或单独更 APK |
| `frontend` / `backend` | 复用已有 APK，只重建主镜像 + 重启（不 pull、不编 APK） | 只改了前端/后端代码 |
| `build` | 只构建主镜像，不重启 | 预构建 |
| `restart` | 不构建，按当前 `.env` 重部署 | 改 `.env` 后生效 |
| `status` | 容器状态 + `/healthz` + 内置版本 | 发版后确认 |
| `logs [-f]` | 查看日志（`-f` 跟随） | 排障 |
| `prune` | 清悬挂镜像 + 构建缓存 | 磁盘占用高时 |
| `stop` | 停止并移除容器（**数据卷保留**） | 临时下线 |

参数（与子命令自由组合）：

| 参数 | 作用 |
|---|---|
| `--no-apk` | `update` 时跳过 APK 编译，复用 `release/` 已有包（前端/后端-only 发版） |
| `--skip-web` | APK 编译跳过前端 vite build（`APK_SKIP_WEB=1`，仅壳页/原生层改动） |
| `--keep-temp` | 成功后不清理工作区中间物（默认构建后自动清理 node_modules / dist / www / gradle 产物） |
| `--skip-git` | 跳过 `git pull`（用工作区当前代码） |
| `--rebuild-builder` | 强制重建 APK 构建镜像（工具链升级、换源） |
| `--no-prune` | 跳过收尾的镜像清理 |

## 四、APK 容器编译（deploy.sh 自动完成，了解即可）

`deploy.sh` 的 `apk` / `update` 会用 **两个容器**完成 APK 编译：

1. **`stickykee-apk-builder` 镜像**（`Dockerfile.apk-builder`）：纯工具链（JDK 17 + Android SDK 34 + Node 20），npm 走 npmmirror、gradle 走腾讯云、maven 走阿里云，国内直连可用。首次构建时生成，之后复用。
2. **`stickykee-apk-cache` 缓存卷**：挂到 `/cache`，持久化 gradle / npm 缓存，二次编译显著提速（实测首编 5min，有缓存 2min 内）。

编译链路（`scripts/build-apk.sh`，等价于旧的 Windows 打包机流程，全在 Linux 容器里跑）：

```
0. 版本一致性校验（4 处 + versionCode，不一致直接 fail，防漏 bump）
1. app：npm ci + vite build        → app/dist
2. 镜像 dist → apk/www（Capacitor webDir，壳页 + 前端产物进 APK）
3. apk：npm ci + cap sync android  → android 工程 assets/插件
4. gradlew assembleRelease（仓库统一 keystore 签名）→ app-release.apk
5. 分发 → release/stickykee-app.apk（主镜像 COPY 输入）
6. 清理工作区中间物（node_modules / dist / www / gradle 产物；release/ 保留）
```

**前置校验**：步骤 0 会检查 4 处版本号一致——所以发版机忘了 `bump-version` 就 push，容器编译会直接报错 `版本不一致（发版前先 bump-version）`，这是设计行为（防旧包冒充新发版）。

## 五、主镜像与 APK 内置机制

单镜像（根 `Dockerfile`）把三端烘焙到一起，数据统一落 `/data` 卷：

| 阶段 | 产物 |
|---|---|
| `node:20-alpine`（npmmirror） | `dist/`（前端静态产物） |
| `golang:1.26-alpine`（goproxy.cn） | `stickynuo`（后端静态二进制） |
| `apkver`（alpine） | 从 `app/package.json` 提取版本号 → `app_version.txt`（**构建期自动生成，无需手工维护**） |
| 运行层（alpine） | 上述 + `COPY release/stickykee-app.apk → /var/apk/` |

- **APK 内置**：`/var/apk/stickykee-app.apk` 随镜像更新自带最新版；`/api/v1/app/download` 提供下载、`/api/v1/app/info` 发版本侧载，App 内更新检测据此比对。
- **版本 sidecar 自动提取**：镜像里 `SN_APK_VERSION_FILE` 由构建期从 `app/package.json` 读取，`/healthz` 与 `/api/v1/app/info` 报的版本即当前发版号——**这就是发版机必须 `bump-version` 的原因**（不改 `package.json`，镜像里的版本不会变）。
- **构建前 `release/stickykee-app.apk` 必须存在**：`COPY` 这步失败会直接构建失败。`update`/`apk` 会自动先编译；`frontend`/`backend`/`build` 复用已有包（缺失时报错提示先 `deploy.sh apk`）。
- **数据卷**：默认命名卷 `stickykee-data:/data`（数据库、IM 图、图标缓存都在 `/data`）。要沿用旧 bind mount，在 `.env` 里设 `VOLUME=/vol2/homecanvas/data:/data`。

## 六、服务器配置（scripts/.env）

`cp scripts/.env.example scripts/.env`（`.env` 已 gitignore，含敏感项不入版本库）。**只填部署层通用项**：

```bash
CONTAINER=stickykee
IMAGE=stickykee:latest
BUILDER=stickykee-apk-builder:latest
PORT=18480                         # 容器用 host 网络，应用直接监听宿主机该端口
VOLUME=stickykee-data:/data        # 或 /vol2/homecanvas/data:/data
RESTART=unless-stopped
TZ=Asia/Shanghai
# SN_LOG_LEVEL=info                # 可选
# BUILDER_BASE=ubuntu:22.04        # 拉不到 docker.io 时指向可达源（如 docker.1ms.run/...）
```

> **业务密钥（HA 地址与 Token、扫码 API key 等）不进 Docker 环境变量**——在应用启动后的「系统配置」页里填。模板只保留通用部署项，避免密钥进 shell 历史 / git。

## 七、统一签名（所有机器产物签名一致）

签名密钥已固化入仓库：`apk/android/app/stickykee.keystore`（别名 `androiddebugkey`，store/key 密码均为 `android`）。`build.gradle` 的 `signingConfigs.stickykee` 同时作用于 **debug 与 release**：

- 任何机器 `git pull` 后容器编译，产物签名一致，可互相覆盖安装，不再依赖各机器 `%USERPROFILE%\.android\debug.keystore`
- 容器里跑的是 `assembleRelease`，产物 `app-release.apk` **已签名**，可直接安装
- **不要删除或更换该 keystore**：签名一变，已装包只能卸载重装（应用数据丢失）
- 指纹核对：SHA1 `ED:3E:E4:D0:EC:CB:5A:17:81:96:45:46:13:2C:00:12:A1:BB:BD:99`

若手机装的是其他签名旧包，覆盖安装报签名冲突——先卸载旧包（数据清空）再装。

## 八、常见问题

| 现象 | 处理 |
|---|---|
| `docker pull ubuntu:22.04` 超时（国内直连 docker.io 不通） | `.env` 设 `BUILDER_BASE` 指向可达源（如 `docker.1ms.run/library/ubuntu:22.04`），`deploy.sh` 会以 `--build-arg BUILDER_BASE=...` 构建；base image 同理可预拉 |
| 容器编译报 `npm ci` 失败 / 前端产物缺 | 宿主 dev server / IDE 占用 `app/node_modules` 原生二进制导致 `EIO`。**关掉本地 dev server** 再跑；脚本已内置 `npm ci` → `npm install` 兜底链 |
| 容器编译报「版本不一致」 | 发版机忘了 `bump-version`，先 `bump-version.ps1 +0.0.1` 再 `git push` |
| 只改了前端/后端，不想重编 APK | `deploy.sh frontend --no-apk`（或 `backend`），复用已有 `release/stickykee-app.apk` |
| 磁盘占高 | `deploy.sh prune`（清悬挂镜像 + 构建缓存；APK 编译缓存卷单独保留以加速） |

## 九、发版核对清单

1. **发版机**：`bump-version.ps1 +0.0.1`（或目标版本），只读校验四处一致（`1.6.12` / `versionCode 41`）
2. `git add` 版本号改动 + 本次功能改动，`git push`
3. **部署机**：`bash scripts/deploy.sh update`
   - 容器编译：`版本一致 → vite → cap sync → gradlew assembleRelease → 分发 release/`
   - 主镜像：`node 编前端 + go 编后端 + 烘焙 APK`
   - 重启 + `/healthz` 健康检查
4. `bash scripts/deploy.sh status` 确认：容器 healthy、`/healthz` 返回新版本、`release/stickykee-app.apk` 存在
5. 手机 App：`/api/v1/app/info` 应发新版本号，App 内更新检测提示可更新（下载 `/api/v1/app/download`）
6. 如改了卡片模板/迁移逻辑：确认 `app/src/utils/dashboard.js` 迁移标记与 `cardDefaults` 模板一致
